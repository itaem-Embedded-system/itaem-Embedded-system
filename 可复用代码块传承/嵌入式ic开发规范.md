# IC 驱动开发规范

## 1. 核心理念与目标

本规范旨在确保 IC 驱动代码具备**高可移植性**、**高稳定性**和**可维护性**。

本规范的底层驱动设计方法，主要参考 ST Standard C Drivers 的平台无关驱动模式：通过 `ctx` 注入 `read/write/delay` 等接口，将器件寄存器逻辑与具体 MCU/HAL 解耦；在此基础上，再叠加本项目对容错、构建完整性、调试链路和代码生成边界的工程化要求。

本规范的演进不是基于单一器件的一次性总结，而是来自多个传感器（至少三个器件）在接入、联调、异常定位和重构过程中的共性经验抽象。因此，文档中的规则优先保留“跨器件、可复用、能落地”的部分，而不追求覆盖所有特殊项目形态。

- **器件驱动（Device）可移植性优先**：器件驱动核心逻辑必须与硬件平台完全解耦，确保无需修改即可移植到不同 MCU。
- **运行期高鲁棒性**：系统必须具备自动检测故障并从错误中恢复的能力（如传感器掉线、数据异常）。
- **分层明确**：严格区分业务逻辑、驱动逻辑与硬件适配层。

## 2. 架构分层原则

### 2.1 分层职责

| 层级                   | 模块位置             | 职责描述                                 | 允许的依赖                     |
| :------------------- | :--------------- | :----------------------------------- | :------------------------ |
| **应用层 (App)**        | `app/`, `main.c` | 业务调度、数据处理、故障监测与恢复、调试输出 (VOFA/Printf) | Device, Middleware, Platform, HAL |
| **器件驱动层 (Device)** | `device/`        | **器件驱动核心逻辑**。处理寄存器协议、状态机、数据转换。      | **仅依赖标准 C 库和 ctx 注入的接口** |
| **中间件层 (Middleware)** | `middleware/`  | 协议、算法、存储、日志等可复用能力模块。                | 标准 C 库, Device         |
| **平台适配层 (Platform)** | `platform/`    | **硬件抽象**。实现具体的 I2C/SPI 读写、延时函数。      | HAL, BSP                  |

### 2.2 严格与灵活的边界

- **Device 层必须“干净”**：严禁包含 `main.h`、`stm32_hal.h` 等硬件相关头文件。严禁直接调用 `HAL_` 开头函数。
- **Middleware 层做能力复用**：协议、算法、日志、存储等通用模块不应承载具体器件寄存器协议。
- **Platform 层允许“脏活”**：允许根据具体芯片实现细节（如 DMA、中断、模拟时序）。
- **App 层负责“兜底”**：负责处理 Device/Middleware 返回的错误，并执行重试或重启策略。

## 3. 强制性规范 (MUST)

### 3.1 可移植性规范

1. **上下文注入**：驱动必须通过结构体指针（`ctx`）传入读写函数、延时函数和句柄，禁止在驱动内部定义全局硬件句柄。
2. **环境隔离**：Device 代码中不得出现特定平台的宏定义（如 `#ifdef STM32F1`），所有平台差异必须通过适配层屏蔽。
3. **HAL 依赖隔离**：Device 层严禁直接调用 HAL 函数（如 `HAL_Delay`），必须通过 ctx 注入的函数指针实现。
4. **生成代码边界隔离**：使用 CubeMX 或其他代码生成工具时，所有用户自定义 include、变量、函数声明和业务逻辑，必须放入 USER CODE、自定义扩展区或独立用户文件中，禁止写入会被生成器覆盖的区域。
5. **上下文字段不得形同虚设**：Platform 层若定义了 `ctx.handle` 或 `ctx.priv_data`，则必须按设计真实消费；禁止一边保留上下文字段，一边在实现中硬编码全局总线句柄、固定片选或固定实例，导致 ctx 只剩形式上的“注入”。

### 3.2 鲁棒性与容错规范

1. **参数强校验**：所有对外接口（API）必须检查指针是否为空、枚举值是否在合法范围内。
2. **超时机制**：所有涉及硬件等待（如 `WaitUntil`、`While`）的循环必须包含超时退出机制。超时时间必须使用宏定义。
3. **通信失败必须有限退出并具备恢复策略**：Platform 层通信函数（如 SPI/I2C 读写）必须保证失败可返回，禁止无限阻塞。默认建议采用有限次重试；若总线存在卡死风险，还应在重试前后加入必要的总线恢复或事务清理步骤。对于实时敏感场景，允许由 App 层接管是否重试与重试次数。
4. **传感器 ID 验证**：初始化时必须读取并验证传感器 ID，确保连接正确的传感器。
5. **初始化时序必须完整**：参考 ST 标准示例，初始化流程至少应覆盖 `platform_init -> boot wait -> device id check -> software reset -> reset complete poll -> key configuration`。其中软件复位后必须轮询确认复位完成，禁止写完复位位后立即继续后续配置。
6. **关键配置回读校验**：初始化中凡是写入工作模式、数据速率、量程、复位位等关键控制寄存器后，必须回读确认配置已真实生效；校验失败必须返回错误，不得静默继续运行。
7. **最小诊断链路保活**：外设初始化失败、配置失败或数据异常时，系统必须保留最小可观测通道（日志、串口、心跳、状态字之一），避免进入“无输出、无状态”的不可诊断状态。
8. **校准区/OTP/系数读取失败不得静默吞错**：初始化阶段凡是读取校准系数、补偿参数、OTP 或器件内部配置镜像时，一旦底层通信失败，必须显式返回错误；禁止以 `0`、默认值或半有效数据代替失败结果继续初始化。
9. **冷启动/复位瞬态治理**：对于连续物理量传感器，若冷启动、软复位或重初始化后的前几帧数据可能污染上位机显示、控制闭环或日志判断，App 层必须具备“预热 + 稳定发布门控”或等价机制。允许内部滤波先收敛，但在稳定条件满足前不得对外发布。
10. **调试链路时间基准统一**：联调期用于波形和日志分析的回传数据，必须包含时间基准（`tick` 或单调递增序号），用于区分“真实物理跳变”和“系统复位/回绕/重启”。
11. **数据异常监测**：应用层必须检查数据合理性（如是否全为 0、是否超出物理量程、是否明显跳变）。典型范围示例：温度 `-50°C ~ 100°C`、压力 `>0 且 <=200000 Pa`、湿度 `0% ~ 100%`。

### 3.3 编码与寄存器操作规范

1. **宏化管理**：所有寄存器地址、位掩码、配置字、命令字、超时时间、重试次数必须使用宏或枚举定义，禁止在流程代码中散落魔数（Magic Number）。
2. **宏的分层归属必须正确**：
    - 器件寄存器地址、位定义、默认配置值、命令字属于 Device 层。
    - 总线实例、片选引脚、DMA 通道、平台超时、平台重试次数属于 Platform 层。
    - 物理量换算阈值、业务告警阈值、滤波参数、QNH 等业务参数属于 App 或 Middleware 层。
3. **寄存器修改必须避免误伤其他位**：修改控制寄存器时，必须保证未涉及的位保持不变；优先采用“读字节 -> 掩码修改 -> 写回”模式。
4. **总线协议附加位必须由 Platform 层处理**：若器件 SPI/I2C/I3C 通信协议要求在读写函数中附加读位、写位、多字节自增位或其他协议控制位，必须在 Platform 层统一处理，不能泄漏到 Device/App 层。
5. **模块内部辅助函数应默认使用内部链接**：仅在模块内部使用的计算、解析、状态判断函数，应优先声明为 `static`，避免无意暴露为跨文件符号。
6. **多字节原始数据拼装必须显式处理字节序与符号扩展**：Device 层在解析 16/24/32 位寄存器原始数据时，必须使用位移与掩码显式拼装，禁止把总线缓冲区直接强转为多字节整型指针。

## 4. 实现模板参考

### 4.1 驱动上下文定义 (Device)

```c
// device/xxx_driver.h
typedef struct {
    int32_t (*write_reg)(void *handle, uint8_t reg, const uint8_t *data, uint16_t len);
    int32_t (*read_reg)(void *handle, uint8_t reg, uint8_t *data, uint16_t len);
    void (*delay_ms)(uint32_t ms);
    void (*lock)(void *handle);
    void (*unlock)(void *handle);
    void *handle;
    void *priv_data;
} xxx_ctx_t;
```

补充约束：

1. `ctx` 只描述驱动所需能力，不暴露具体 HAL 名称。
2. `handle` 只做平台对象透传，例如 SPI 句柄、I2C 句柄或组合句柄。
3. `priv_data` 为可选项，用于额外平台上下文；项目暂不需要时可以不启用。
4. `lock/unlock` 主要用于 RTOS、多任务或共享总线场景；裸机单循环工程可不启用。
5. Device 层对 `ctx` 的使用必须是无状态或最小状态的，禁止把平台资源缓存为模块级全局变量。
6. 多总线实例或多个同型器件必须依赖 `ctx` 区分，禁止靠文件内静态全局句柄切换目标设备。

### 4.2 寄存器建模与访问模式

#### 4.2.1 读改写是默认模式

对控制寄存器的常规修改，默认应采用以下模式：

```c
uint8_t reg_val;

ret = xxx_read_reg(ctx, XXX_CTRL_REG, &reg_val, 1);
if (ret != 0) {
    return ret;
}

reg_val &= (uint8_t)(~XXX_CTRL_ODR_Msk);
reg_val |= ((uint8_t)odr << XXX_CTRL_ODR_Pos);

ret = xxx_write_reg(ctx, XXX_CTRL_REG, &reg_val, 1);
return ret;
```

约束：

1. 先读后改，避免覆盖保留位和其他功能位。
2. 掩码和位移必须由宏统一定义，不能直接写裸常数。
3. 写回后如该寄存器属于关键控制项，应继续执行回读校验。
4. 多字节连续读写位等总线协议细节，由 Platform 读写函数处理。

#### 4.2.2 跨寄存器字段必须显式拆分与重组

若一个逻辑配置项分散在多个寄存器中，驱动层必须提供统一封装接口，由驱动内部负责拆分与重组，不能把拼装细节泄漏给 App 层。

```c
uint8_t combined_val;

combined_val = ((reg_high_field << 4) | reg_low_field);
```

要求：

1. `set` 接口内部完成位拆分并分别写入多个寄存器。
2. `get` 接口内部完成多个寄存器字段读取与重组。
3. App 层只面对语义化枚举值，不直接操作碎片化位段。
4. 对多字节原始数据，必须通过移位和掩码显式处理字节顺序与符号扩展。

#### 4.2.3 位域映射的使用边界

1. 位域主要用于提升寄存器语义可读性，不应替代全部寄存器访问策略。
2. 涉及跨编译器、跨架构、对齐不确定性的项目，优先使用掩码宏。
3. 若采用位域，必须明确大小端处理方式，并确认结构体大小与目标寄存器宽度严格一致。

### 4.3 容错恢复逻辑 (App)

```c
// app/xxx_app.c
void XXX_Loop(void) {
    int ret = xxx_read_data(&ctx, &data);

    if (ret != 0) {
        error_count++;
    } else if (data.temperature < -50.0f || data.temperature > 100.0f ||
               data.pressure <= 0 || data.pressure > 200000) {
        error_count++;
    } else {
        error_count = 0;
    }

    if (error_count > MAX_ERROR_THRESHOLD) {
        xxx_reset(&ctx);
        xxx_init(&ctx);
        error_count = 0;
    }
}
```

### 4.4 初始化最小闭环

建议顺序：

1. 基础平台初始化成功。
2. 最小诊断链路可用。
3. 完成 boot wait。
4. 器件 ID 校验通过。
5. 必要时执行软件复位，并轮询确认复位结束。
6. 写入关键寄存器并回读确认。
7. 校准系数、OTP 或关键补偿参数读取成功。
8. 进入业务循环前，至少完成一次系统状态、器件状态、业务数据的联调验证。

### 4.5 Platform 层事务重试模板

```c
#define XXX_BUS_TIMEOUT_MS   10U
#define XXX_BUS_RETRY_COUNT  3U

static int32_t XXX_ReadReg(void *handle, uint8_t reg, uint8_t *data, uint16_t len)
{
    uint32_t retry;

    for (retry = 0; retry < XXX_BUS_RETRY_COUNT; retry++) {
        XXX_Select(handle);

        if (Bus_SendCmd(handle, reg) != 0) {
            XXX_Deselect(handle);
            continue;
        }

        if (Bus_ReadData(handle, data, len) != 0) {
            XXX_Deselect(handle);
            continue;
        }

        XXX_Deselect(handle);
        return XXX_ERR_NONE;
    }

    return XXX_ERR_COMM;
}
```

约束：

1. 重试次数必须有限且宏化，禁止无限重试。
2. 每次失败后都必须完整收尾，例如释放 CS、清状态位、恢复总线空闲态。
3. 默认重试应发生在 Platform 层；若项目对实时性极敏感，可由 App 层基于返回码决定是否继续重试。
4. 若总线事务存在时序要求，重试前必须补足必要延时或恢复序列。

### 4.6 生成文件边界规范

1. 业务 include、模块头文件、静态变量、函数原型放入 USER CODE 对应区域。
2. 复杂业务逻辑尽量放入 `app/`、`device/`、`platform/` 等独立文件，生成文件仅保留调用入口。
3. 不要把关键初始化、通信流程、状态机主体直接写在生成器可覆盖区。
4. 每次重新生成后，至少检查 include 区、私有变量区、函数声明区和主循环调用点是否仍完整。

## 5. 推荐性规范与联调建议 (SHOULD)

1. **非阻塞延时**：在应用层轮询（Loop）中，建议使用基于时间戳（Tick）的非阻塞调度，避免使用 `HAL_Delay` 阻塞 CPU。
2. **调试分离**：调试代码（如 VOFA+ 波形发送、Printf 日志）应置于 `main.c` 或独立调试模块中，**严禁**混入 `device` 驱动文件。
3. **错误码统一**：建议定义错误码枚举统一错误表示，例如：
   ```c
   typedef enum {
       XXX_ERR_NONE = 0,
       XXX_ERR_PARAM = -1,    // 参数错误
       XXX_ERR_COMM = -2,     // 通信错误
       XXX_ERR_TIMEOUT = -3,  // 超时
       XXX_ERR_CONFIG = -4,   // 配置错误
       XXX_ERR_ID = -5,       // ID 不匹配
   } XXX_Error_t;
   ```
4. **寄存器操作优先采用掩码字节读改写**：对于控制寄存器，优先采用“读字节 -> 掩码修改 -> 写字节”的方式，避免依赖位域布局造成跨编译器、跨平台差异。
5. **位域仅作受控场景下的表达工具**：若必须使用位域结构体映射寄存器，必须满足以下条件：
    - 仅映射单字节寄存器，不跨字节拼接位域。
    - 明确字节序条件编译，避免不同编译器布局差异。
    - 不将位域结构体作为通用线协议序列化格式。
    - 对可移植性要求高的项目，仍应优先选择掩码宏而非位域。
6. **正式协议如资源允许也建议保留时间基准**：即便脱离联调阶段，在波形、日志或二进制流中仍建议保留 `tick`、序号或帧计数，以便后续定位“发送链路异常”和“业务数据未刷新”。
7. **对外读取接口应尽量无副作用**：类似 `get`、`read_cached`、`channel_get` 的接口，建议只返回当前状态或缓存值，不顺带推进状态机、清错误计数或触发总线访问；若接口确有副作用，应在命名和注释中明确说明。
8. **共享总线项目建议显式提供并发保护方案**：若项目运行在 RTOS、多任务或中断/线程共享总线环境中，建议在 Platform 层提供互斥、锁或总线仲裁方案，避免多个调用者并发访问同一总线或同一器件。

### 5.1 分级回传测试

用于联调期快速确认链路与状态，不追求复杂协议实现。

1. **按三组信息顺序测试**：
    - 系统/MCU 运行状态
    - 传感器/模块初始化状态
    - 业务采样数据
2. **按项目现有链路逐级降级验证**：遵循“从顶层到底层、从复杂到简单”的原则逐级回传，层数不固定，以能快速定位问题为准。
3. **失败继续**：上一层协议失败，不阻塞下一层协议验证。
4. **先验证、后常态化**：三组验证完成后，再切回常用协议进入正式循环。
5. **保持轻量**：简单测试只要求能看见状态变化与链路连通，不要求一次性引入复杂校验和大量字段。
6. **联调探测代码必须可收口**：模式扫描、临时测试帧、分级探测分支只能服务联调定位；定位完成后应回归单一稳定路径，避免临时代码长期影响主流程。

注：如项目已有明确协议栈，可按项目约定将“复杂 -> 简单”映射到具体协议；若接收到异常数据，也应保留最小回传能力，避免再次进入不可诊断状态。

## 6. 评审自检清单 (Checklist)

在提交代码前，请对照以下清单自查：

- [ ] **依赖检查**：`device` 文件夹下的 `.c` 文件是否包含了 `main.h` 或 `stm32_hal.h`？（如果有，请删除）
- [ ] **上下文注入完整**：`ctx` 结构体是否包含了所有必要的函数指针（如 `delay_ms`）？
- [ ] **上下文字段真实使用**：`ctx.handle` / `ctx.priv_data` 是否被 Platform 实现真实使用，而不是保留字段却硬编码全局资源？
- [ ] **参数校验**：`set_xxx` 函数是否检查了参数范围？
- [ ] **超时保护**：`while` 循环是否有超时计数器？
- [ ] **通信重试**：Platform 层通信函数是否实现了重试机制？
- [ ] **失败有限退出**：所有底层通信失败后，是否都能在有限时间内返回，而不是卡死在轮询或重试里？
- [ ] **传感器 ID 验证**：初始化函数是否读取并验证了传感器 ID？
- [ ] **初始化时序完整**：是否执行了 boot wait、ID 检查、软件复位以及复位完成轮询？
- [ ] **校准读取显式报错**：校准区、OTP、系数读取失败时，是否显式返回错误而不是以 0 或默认值继续？
- [ ] **数据校验**：应用层是否检查了温度/压力等数据的合理范围，以及全 0、乱码、明显跳变等异常模式？
- [ ] **错误码统一**：是否定义了错误码枚举，避免使用魔数？
- [ ] **宏定义位置**：寄存器地址、位掩码、命令字是否放在 Device 层；CS、总线句柄、重试次数等平台细节是否放在 Platform 层？
- [ ] **协议附加位处理**：SPI/I2C 多字节位、读写控制位等是否统一封装在 Platform 读写函数中？
- [ ] **字节序与拼装**：多字节原始数据是否通过移位/掩码显式拼装，未出现直接强转缓冲区的写法？
- [ ] **生成文件边界**：CubeMX 或其他生成文件中的自定义 include、变量、原型和业务调用，是否全部位于 USER CODE 或独立用户文件中？
- [ ] **调试代码**：`device` 中是否残留了 `printf` 或串口发送代码？（请移至 `app` 或 `main`）
- [ ] **恢复机制**：拔掉传感器再插上，系统能否自动恢复数据输出？
- [ ] **内部符号收口**：仅模块内部使用的辅助函数是否已使用 `static` 收口，避免形成无意的外部接口？
- [ ] **分级回传**：系统状态、初始化状态、业务数据三组信息是否都进行了“复杂到简单”的逐级回传验证？
- [ ] **瞬态发布门控**：对于连续物理量传感器，冷启动/复位后是否通过预热+稳定门控（或等价策略）避免异常尖峰直接对外发布？
- [ ] **时间基准回传**：联调数据是否包含 `tick` 或等价单调序号，便于定位复位点与回绕点？
- [ ] **联调代码收口**：模式扫描、测试帧等临时探测代码是否已清理或开关化管理，并默认关闭？
- [ ] **读取接口副作用**：对外 `get/read` 类接口是否避免隐式推进状态机、清计数或触发额外总线访问；若存在副作用，是否已显式命名说明？
- [ ] **共享总线保护**：若项目存在 RTOS、多任务或中断/线程共享总线，是否已有互斥或总线仲裁方案？
- [ ] **寄存器读改写**：控制寄存器修改是否采用读改写或等价保护方式，避免误写其他位？
- [ ] **多寄存器字段封装**：跨寄存器配置项是否由 Device 层统一封装，未泄漏到 App 层？
- [ ] **位域风险审查**：如使用位域映射寄存器，是否明确了字节序、结构体宽度和适用边界？

## 7. 常见失效模式抽象

以下内容不是针对某一颗具体芯片，而是从实际联调问题中抽象出的通用失效模式：

### 7.1 构建不完整

- 现象：代码逻辑看似已接入，但目标文件、头文件路径或宏配置未进入构建系统，最终表现为功能缺失、链接缺符号，或行为与源码不一致。
- 约束：新增模块时，必须同步检查构建系统中的 `target_sources`、`target_include_directories`、宏定义与条件编译项。

### 7.2 初始化失败后阻塞主循环

- 现象：某个外设初始化失败后直接 `while(1)`，导致系统失去诊断输出与后续恢复机会。
- 约束：初始化失败应优先返回错误并交由上层实施限频重试、状态上报或降级运行，而不是永久阻塞。

### 7.3 初始化顺序残缺

- 现象：只做了设备 ID 检查或只做了寄存器配置，没有执行 boot wait、软件复位、复位完成轮询等完整上电序列，导致器件偶现不启动、配置不生效或首包数据异常。
- 约束：初始化流程必须至少覆盖上电等待、ID 校验、复位恢复、关键配置与必要回读；不能把 ST 标准示例中的上电顺序裁掉一半。

### 7.4 寄存器语义只剩“结论”没有“方法”

- 现象：规范里只保留了“要解耦、要可移植、要可靠”这些结论，但缺少最关键的寄存器建模方法，导致后续实现容易回退到裸写寄存器、魔数散落或 App 层拼寄存器。
- 约束：规范除了给出分层结论，还必须保留“ctx 注入”“读改写”“多寄存器字段统一封装”“位域使用边界”这类可直接落地的实现方法。

### 7.5 代码生成后用户逻辑丢失

- 现象：CubeMX 或类似工具重新生成后，自定义 include、变量、函数声明或调用入口被覆盖，表现为编辑器大面积报错、链接失败或运行逻辑丢失。
- 约束：所有用户扩展必须固定落在 USER CODE 或独立文件；每次生成后必须做一次最小回归检查，确认入口仍然存在。

### 7.6 校准读取失败被伪装成合法默认值

- 现象：读取校准系数、OTP 或补偿参数失败后，驱动把结果默默置为 `0` 或默认值，初始化表面成功，但后续物理量计算持续错误。
- 约束：校准链路一旦失败，必须立即返回通信错误或配置错误；禁止把“未读到”伪装成“刚好读到 0”。

### 7.7 ctx 注入存在但平台仍硬编码资源

- 现象：接口设计上保留了 `ctx.handle` 或 `ctx.priv_data`，实际实现却直接绑定 `hspi1`、固定 GPIO 或固定外设实例，导致多实例、多器件或迁移时失效。
- 约束：若采用 ctx 注入，就必须让 Platform 实现真实依赖 ctx 传入的平台对象；否则宁可删掉无效字段，也不要制造“伪注入”接口。

### 7.8 复位后首包尖峰直接外发

- 现象：系统复位或传感器重初始化后，最初几帧出现明显跳变（压力/海拔突刺），上位机误判为真实物理变化。
- 约束：对于连续物理量传感器，在 App 层增加“预热收敛 + 稳定发布门控”策略。内部可持续滤波和状态更新，但在连续稳定样本达到阈值前不对外发布。
- 诊断要点：调试回传必须带 `tick` 或序号，先定位是否存在复位点，再区分“复位瞬态”与“真实环境突变”。

### 7.9 多字节原始数据解析被直接强转

- 现象：开发者把 `uint8_t buf[]` 直接强转成 `uint16_t*`、`int16_t*` 或 `int32_t*` 使用，导致字节序错误、未对齐访问风险或 24 位补码符号扩展错误。
- 约束：所有多字节寄存器值必须通过移位、掩码和显式符号扩展完成拼装，不能依赖编译器、平台字节序或未定义的内存对齐行为。
- 诊断要点：重点检查 16 位以上原始量的拼装函数，确认是否存在指针强转、联合体偷读或未处理高位符号位的情况。
